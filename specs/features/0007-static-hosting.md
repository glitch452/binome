# Feature Spec — Static Build & Hosting

Status: **planned** · Owner: glitch452 · Related: `specs/requirements.md` §19,
`specs/tasks/0007-static-hosting-tasks.md`

## 1. Summary

Switch the Next.js build output from `standalone` (Node.js server) to `export` (static HTML/CSS/JS files in `out/`),
then re-platform the two delivery targets to match: replace the Docker runner with a lightweight **nginx:alpine**
container that serves the static bundle, and add a **GitHub Pages** deployment to the release workflow so every new
semver release is also published to a custom domain. The app's client-side architecture (no server actions, no API
routes, every component `'use client'`) makes it a natural fit for a pure static host; this change eliminates the
Node.js runtime from both deployment paths while keeping the existing PWA (Serwist service worker) and update-check
(`/build-info.json`) behaviour intact.

## 2. Goals

- Change `next.config.ts` to `output: 'export'` so `npm run build` produces a fully static `out/` directory deployable
  to any web server.
- Update `Dockerfile` to use `nginx:alpine` as the runner stage, serving `out/` — no Node.js runtime in the final image.
- Add an `nginx.conf` that sets correct cache headers (`/_next/static/` immutable, `sw.js` and `build-info.json`
  no-cache) and the `Service-Worker-Allowed: /` header.
- Add a `deploy-pages` job to `.github/workflows/release.yml` that builds the static bundle and deploys `out/` to GitHub
  Pages on every new semver release, gated identically to the Docker push.
- Support a **custom domain at root `/`** via `public/CNAME`, so no `basePath` change is needed in Next.js config.
- Update the `build` script to copy Serwist-generated service worker artifacts (`sw.js`, `sw.js.map`, `swe-worker-*.js`)
  from `public/` into `out/` after the Serwist build step, since `next build` with static export copies `public/` to
  `out/` _before_ Serwist runs.
- Ensure the existing PWA installation, service worker precaching, and `/build-info.json` NetworkFirst polling continue
  to work unchanged in both deployment environments.

## 3. Non-Goals (v1 of this feature)

- **No custom domain DNS setup** — adding the `CNAME` record and verifying the domain in GitHub is a deployment concern
  handled outside the repo.
- **No removal of Docker** — both Docker (nginx) and GitHub Pages coexist; Docker is for self-hosting, Pages is the
  public demo.
- **No PR preview deployments** — GitHub Pages deploys only on new releases, not on every PR.
- **No Serwist config changes** — `serwist.config.mjs` continues to use `@serwist/next/config`; it reads `.next/`
  manifests at build time regardless of output mode, so no reconfiguration of the precache logic is required.
- **No separate static-export build script** — a single `build` script produces the `out/` directory used by both Docker
  and GitHub Pages.
- **No local multi-arch builds** — cross-compilation is handled by GitHub Actions (QEMU + Buildx); `docker build` on a
  developer's machine produces a single native-platform image as before.

## 4. Build Strategy — Static Export

### 4.1 Next.js config

Change `next.config.ts`:

```ts
const nextConfig: NextConfig = {
  output: 'export',
};
```

With `output: 'export'`, `next build` emits a fully static `out/` directory. The `out/` layout:

```
out/
  index.html              ← the app shell
  404.html                ← Next.js-generated 404
  _next/static/…          ← hashed JS/CSS chunks
  icons/                  ← copied from public/
  sounds/                 ← copied from public/
  build-info.json         ← generated by prebuild script
  manifest.webmanifest    ← emitted from app/manifest.ts metadata route
  CNAME                   ← copied from public/CNAME (§7)
  sw.js                   ← copied after serwist build (§4.2)
  sw.js.map               ← copied after serwist build
  swe-worker-*.js         ← copied after serwist build
```

No `next/image` optimization is used in the codebase (all icons are inline SVG via lucide-react), so
`images.unoptimized` is not required. Verify with a build if any `<Image>` usage is ever added.

### 4.2 Build script and Serwist artifact copy

Static export copies `public/` to `out/` during `next build`, but `serwist build` runs _after_ `next build` and writes
`public/sw.js`, `public/sw.js.map`, and `public/swe-worker-*.js`. Those files therefore do **not** land in `out/`
automatically. The `build` script must copy them explicitly:

```json
"build": "next build && serwist build serwist.config.mjs && node scripts/copy-sw-to-out.js"
```

`scripts/copy-sw-to-out.js` is a small Node.js script (no new deps) that copies all matching `public/sw*.js*` and
`public/swe-worker-*.js` files into `out/`, using `fs.cpSync` with a glob. Using a script (rather than a raw `cp`
command) keeps the build cross-platform.

### 4.3 `npm run start`

`next start` requires the standalone output and breaks with `output: 'export'`. Update the `start` script to serve the
`out/` directory locally using `npx serve`:

```json
"start": "npx serve out"
```

This is only for local inspection of the production build. The canonical production runtime is Docker or GitHub Pages.

## 5. nginx Configuration

Add `nginx.conf` at the repo root. This file is `COPY`-ed into the Docker runner stage and is not served to users.

```nginx
server {
  listen 80;
  root /usr/share/nginx/html;
  index index.html;

  # Immutable cache for hashed Next.js static chunks
  location /_next/static/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
  }

  # No-cache for service worker — must always be fresh
  location = /sw.js {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
    add_header Service-Worker-Allowed "/";
  }

  # No-cache for swe-worker bundle (same reasoning as sw.js)
  location ~* ^/swe-worker-.*\.js$ {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
  }

  # No-cache for build-info.json so the update-check poll fetches the latest version
  location = /build-info.json {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
  }

  # SPA fallback: unknown paths fall back to 404.html (Next.js-generated)
  error_page 404 /404.html;
  location / {
    try_files $uri $uri.html $uri/ /index.html;
  }
}
```

Key decisions:

- **Port 80** — the standard nginx default. `docker-compose.yml` maps `3000:80` so the external interface is unchanged.
- **`try_files $uri $uri.html`** — handles Next.js's default no-trailing-slash output (e.g. a future `/about` route
  would be at `out/about.html` and be found by `$uri.html`).
- **`Service-Worker-Allowed: /`** — sets the SW's maximum allowed scope to `/` even when served from a sub-path in any
  future hosting scenario.

## 6. Docker Update

### 6.1 Dockerfile

Replace the existing three-stage build (`deps` → `builder` → Node runner) with a two-stage build (`builder` → nginx
runner). The `deps` stage is no longer needed since nginx doesn't serve Node.js.

```dockerfile
# Stage 1: builder
FROM node:24-alpine AS builder
WORKDIR /app
ARG BUILD_VERSION
ARG GIT_SHA
ENV BUILD_VERSION=$BUILD_VERSION
ENV GIT_SHA=$GIT_SHA
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: nginx runner — serves the static export
FROM nginx:alpine AS runner
COPY --from=builder /app/out /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
```

The final image contains only nginx and the static files — no Node.js, no `node_modules`, no source.

### 6.2 Multi-arch build in CI

The Dockerfile is already platform-agnostic (`node:24-alpine` and `nginx:alpine` are both multi-arch images). The only
change required is in the CI `release` job: add QEMU emulation and Docker Buildx before the existing build-push step,
then declare `platforms` on that step.

Steps to add to `release.yml` (immediately before the existing "Build and push Docker image" step):

```yaml
- name: Set up QEMU
  if: steps.semver.outputs.new_release_published == 'true'
  uses: docker/setup-qemu-action@v3

- name: Set up Docker Buildx
  if: steps.semver.outputs.new_release_published == 'true'
  uses: docker/setup-buildx-action@v3
```

The existing `docker/build-push-action` step gains one new field:

```yaml
platforms: linux/amd64,linux/arm64
```

`linux/arm64` covers Apple Silicon Macs and AWS Graviton instances. QEMU handles the cross-compilation on the
`ubuntu-latest` runner; the build is slower than native but requires no separate runners.

### 6.3 docker-compose.yml

Update the port mapping from `3000:3000` to `3000:80` (nginx listens on port 80 internally):

```yaml
services:
  app:
    build: .
    ports:
      - '3000:80'
    restart: unless-stopped
```

## 7. GitHub Pages Deployment

### 7.1 Repository prerequisites (manual, outside the repo)

Before the workflow will succeed, the repository owner must:

1. Go to **Settings → Pages → Build and deployment** and set the source to **GitHub Actions**.
2. Add a custom domain in the GitHub Pages settings and verify it.

These steps cannot be automated via workflow files.

### 7.2 `public/CNAME`

Add `public/CNAME` containing the custom domain (one line, no trailing newline). `next build` copies `public/` to
`out/`, so `out/CNAME` is present in the uploaded Pages artifact. Example content:

```
example.com
```

Replace `example.com` with the actual custom domain before enabling Pages.

### 7.3 Workflow changes — `release.yml`

Add a `deploy-pages` job to `.github/workflows/release.yml`. This job:

- Runs `needs: release` (after the release job completes)
- Is conditioned on `needs.release.outputs.new_release_published == 'true'` — same gate as the Docker push
- Holds only the permissions it needs (`pages: write`, `id-token: write`, `contents: read`)
- Uses the `github-pages` deployment environment

The release job must be updated to **export the `new_release_published` and `new_release_version` outputs** so the
downstream `deploy-pages` job can read them.

```yaml
# Output additions to the release job:
outputs:
  new_release_published: ${{ steps.semver.outputs.new_release_published }}
  new_release_version: ${{ steps.semver.outputs.new_release_version }}
```

```yaml
deploy-pages:
  name: Deploy to GitHub Pages
  needs: release
  if: needs.release.outputs.new_release_published == 'true'
  runs-on: ubuntu-latest
  environment:
    name: github-pages
    url: ${{ steps.deployment.outputs.page_url }}
  permissions:
    pages: write
    id-token: write
    contents: read

  steps:
    - name: Checkout
      uses: actions/checkout@v6

    - name: Setup Node.js
      uses: actions/setup-node@v6
      with:
        node-version-file: '.nvmrc'

    - name: Install Dependencies
      run: npm ci

    - name: Build Static Export
      run: npm run build
      env:
        BUILD_VERSION: ${{ needs.release.outputs.new_release_version }}
        GIT_SHA: ${{ github.sha }}
        HUSKY: '0'

    - name: Upload Pages Artifact
      uses: actions/upload-pages-artifact@v3
      with:
        path: ./out

    - name: Deploy to GitHub Pages
      id: deployment
      uses: actions/deploy-pages@v4
```

The `deploy-pages` job runs `npm ci` and `npm run build` independently of the Docker build that runs inside the
Dockerfile — the build runs twice, which is acceptable given that the static export build is fast and keeps the two
delivery targets self-contained.

## 8. Data Models & Validation

No change to the data model. `TimerConfig`, `timerConfigSchema`, `parseTimerList`, and all `localStorage` keys are
untouched. This feature modifies only build configuration, deployment infrastructure, and CI/CD workflow files.

## 10. UX Notes

This feature makes no changes to the app's UI, interaction model, or visual design. The delivered experience is
identical to the current app. The only user-visible difference is the deployment URL (GitHub Pages custom domain) and a
potentially faster asset serving from nginx's efficient static-file handling.

The active-timer-safety contract (`skipWaiting: false`, no auto-reload on reconnect) is unchanged — the PWA update flow
continues to work the same way regardless of which static host serves the files.

## 11. Testing Strategy

All verification for this feature is build/infrastructure-level — there are no logic changes to test with Vitest.

- **`scripts/copy-sw-to-out.js`** — **(no unit test)** Verified by running `npm run build` and confirming `out/sw.js`,
  `out/sw.js.map`, and `out/swe-worker-*.js` are present.
- **`next.config.ts`** — **(no unit test)** Verified by `npm run build` producing `out/index.html` and no
  `.next/standalone/` directory.
- **`nginx.conf`** — **(no unit test)** Verified by `docker build` succeeding and `docker compose up` serving the app at
  `http://localhost:3000`, with response headers confirming the cache-control rules.
- **`.github/workflows/release.yml`** — **(no unit test)** Verified by a manual release triggering both the Docker push
  and the GitHub Pages deployment.

## 12. Edge Cases

- **`sw.js` missing from `out/`** — if the copy step fails or is omitted, the PWA cannot install/update. The
  `scripts/copy-sw-to-out.js` script should throw on copy failure so the build fails loudly rather than silently
  shipping a broken PWA.
- **`swe-worker-*.js` glob matches nothing** — if Serwist does not emit `swe-worker-*.js` files in a future version, the
  copy script should not fail; it should silently skip non-matching globs.
- **`public/CNAME` missing** — GitHub Pages will serve from the `github.io` subdomain. The app still works, but the
  custom domain is not applied. The `CNAME` file must be present before enabling the custom domain in GitHub settings.
- **Double build in CI** — `npm run build` runs twice per release (once inside Docker, once in `deploy-pages`). The two
  builds are independent and each bakes the correct `BUILD_VERSION`/`GIT_SHA` env vars. This is intentional and
  acceptable; an optimization to share artifacts can be done in a future pass if build time becomes a concern.
- **`next start` removed** — anyone running `npm run start` locally now starts `npx serve out`. If `out/` does not exist
  (no prior `npm run build`), `serve` will fail with a clear error. The `npm run dev` workflow is unaffected.
- **`output: 'export'` with future server features** — if any future feature adds server actions, API routes, or dynamic
  rendering, the build will fail at `next build`. This is intentional — the static-export constraint is now enforced by
  the build pipeline.

## 13. Rollout Notes

- **No new runtime dependencies.** `nginx:alpine` replaces `node:24-alpine` in the runner stage at no extra cost.
  `npx serve` in the `start` script uses `npx` on-demand (not a declared dependency). `scripts/copy-sw-to-out.js` uses
  Node's built-in `fs` module only.
- **New dev dependency: none.** `scripts/copy-sw-to-out.js` is a plain Node.js script; no new package is needed.
- **Docs to update (as part of implementation, not now):**
  - `specs/requirements.md` §11 (Docker Deployment) — update the runner description from standalone+Node to nginx+static
    export; update the copy commands and port notes.
  - `specs/requirements.md` — add **§19 Static Hosting & GitHub Pages** covering the `output: 'export'` strategy, the SW
    copy step, the nginx config, the `public/CNAME` approach, and the `deploy-pages` workflow job.
  - `CLAUDE.md` — update the "Docker" and "Expected Commands" sections: `output: 'standalone'` → `output: 'export'`,
    `npm run start` → `npx serve out`, Docker runner → nginx:alpine, note the `public/CNAME` file and the `deploy-pages`

- **No persisted-data migration required.** This is a build and deployment change only; all `localStorage` keys,
  `TimerConfig`, and preference types are untouched.
- **Repository settings required before first Pages deploy** — enable GitHub Actions as the Pages source and configure
  the custom domain in the repo's Pages settings. These one-time steps are outside the codebase.
